# Functional service statistics

The goal is useful measurement across the widest supportable population without
an unnecessary permission dialog. This path counts functional requests that
already reach app-tracking. It emits no extra client request and needs no usage
grant. The [measurement decision](adr/0010-metrics-purposes-and-consent.md) owns
the broader assessment and accepted uncertainty.

## Implemented scope

For a valid catalog version route, count the returned `200`, `304`, or `503`.
Store only server UTC day, reviewed tool/distribution/channel, response status,
and aggregate count. Each request increments a shared group directly. There is
no request-level event, receipt, installation ID, IP/IP hash, user agent, device
query, repository field, exact request timestamp, or local client queue.
Invalid requests, health, admin, and telemetry requests are excluded. No
local/CI classification is inferred from headers or addresses.

Each daily group caps at one trillion requests. Counters are retained for 24
calendar months, excluded from reads on expiry, and removed by bounded
maintenance. These service groups contain no individual history to link or
delete. They do not enter monthly history, cross-tool profiles, or public-usage
publication.

`DNT: 1` and `Sec-GPC: 1` exclude a request from optional statistics.
`UpdateClient::with_service_metrics(false)` sends DNT while preserving updates;
the host maps its analytics disable setting and `DO_NOT_TRACK` to this builder.
The SDK reads no environment implicitly. The same control works locally and
on CI. Declining additional local reporting does not disable these aggregate
functional-request statistics; use the independent service-statistics opt-out.

## Assessment and limits

The selected design uses route values needed to answer the requested lookup
and response categories generated by the service. It initiates no additional
terminal storage/access for analytics. This follows the distinction in
[LfDI Baden-Wuerttemberg's FAQ, section 3.1](https://www.baden-wuerttemberg.datenschutz.de/faq-zu-cookies-und-tracking-2/)
between automatically received requests and actively obtaining more device
information. The March 2022 FAQ is supporting guidance, not a CLI-specific
ruling; read it with the [DSK's November 2024 guidance, paragraphs 13-15 and 88-95](https://www.datenschutzkonferenz-online.de/media/oh/OH_Digitale_Dienste.pdf).

The purpose is to understand demand for delivery routes and maintain service
availability. Immediate grouping avoids user profiles. This supports using
legitimate interests for incidental personal-data processing before aggregation,
subject to actual transparency, necessity, balancing, and processor duties.
This is an engineering/legal assessment, not approval by an authority. Network
providers still process connection metadata; the database receives only the
aggregate dimensions above. Processor, region, transfer, logging, and public
privacy disclosures must cover that processing. The collection switch is an
operator setting, not consent from the people using a tool.

A new CLI analytics request is a different acquisition path. Command/version
or local language-use reporting needs a separate assessment even without an
identifier. Current rich events retain their opt-in route. U01-U13 in the
measurement decision explain the narrower candidates and contrary evidence.

## Coverage and delivery

The unit is **origin version requests**, never users, installations, active
repositories, CLI invocations, or installed-version adoption. A response
advertises a release; it does not reveal the installed version. Distribution
aliases are requested routes, not proof of a package manager.

Only requests executing this script are counted. CDN hits outside the script,
client cache hits, offline use, opt-outs, isolate teardown, the eight-pending-write
limit, and storage failures reduce coverage. CDN request statistics would be a
distinct source. Do not disable caching or issue synthetic requests to inflate
coverage. Anonymous clients can generate traffic; counts do not authenticate
human use.

Writes use [Bunny's documented `Bunny.v1.waitUntil`](https://bunny.net/docs/scripting/runtime),
a one-second network cancellation signal, and no application retry. Unknown
commit outcomes must not increment twice. A missing background runtime hook
disables collection. Statistics failures cannot change the update response or
its cache/ETag behavior. Accounting is best effort.

## Deployment and private reads

Migration `0013-service-statistics.sql` adds the table, constrained write,
aggregate read, and cleanup functions. Runtime gets only
`count_version_request_v1`; reporting gets only `admin_service_requests_v1`.
Neither gets table access or the other role's capability. The migration also
prevents opt-out event definitions from selecting device/project collectors.

Set repository variable `APP_TRACKING_SERVICE_METRICS_ENABLED=1` for the next
normal deployment after updating the public privacy disclosure. This is
independent of `APP_TRACKING_TELEMETRY_ENABLED`. `configure-telemetry.ts`
applies migrations and grants when either path is enabled. An unset switch
leaves existing deployments off. Rollback requires both the artifact and the
current switch to support collection. Editing these files performs no deployment.

`GET /v1/admin/service-requests?from=2026-10-01&until=2026-10-29&tool=all`
uses existing WorkOS session and same-origin checks. `from` is inclusive,
`until` exclusive, with at most 90 days per query; query 24-month history in
bounded windows. Tools are `all`, `dalo`, or `palamedes`. Other parameters,
including client/CI/project filters, are rejected. Results contain
`schema_version`, `period`, `scope`, `coverage`, and aggregate `rows` with
decimal-string counts. Expired windows return `outside_retention`. This API
serves authenticated reporting clients; the existing dashboard retains its
separate opt-in usage series.
